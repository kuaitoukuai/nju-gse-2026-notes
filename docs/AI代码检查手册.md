## 0. 三十秒版

AI 写的代码不要靠「读一遍觉得没问题」来验收。把代码当黑盒，用**外部可检查的证据**判断对不对：

1. 先把「对」写成第三人能判定的验收条件；
2. 用等价类 / 边界值 / 决策表 / 状态转换设计输入；
3. 断言由人写，让 CI 有约束力；
4. 拿不到标准答案时，用差分测试、属性测试、模糊测试；
5. 高风险模块上形式化证明；
6. 最后问一句：这个绿色对勾，究竟买到了什么？

## 1. 核心立场：不信任作者，只信任证据

第 12 讲在讲「携带证明的代码」时把责任分工说得很清楚：

> 代码提供者承担构造证明的工作，接收者根据自己的安全策略检查证明。**接收者不必因为「作者值得信任」或「模型看起来很厉害」就接受代码。**

第 8 讲把同一逻辑说得更直接：

> Ralph Loop 中一个关键要求是：每轮都验证并评估结果。其出发点可以说得很不客气：**开发者是不可信的。** 这里的人类开发者也一样——「我只改了一点点，不会有事」，往往正是事故的开场白。

这两句话决定了后面所有方法的方向：**检查的对象不是「作者靠不靠谱」，而是「产物能不能被证据支持」。**

第 1 讲进一步解释了为什么不能靠读：

> 生成可以越来越快，**逐行阅读却难以同样加速**。新的工程工作因此更依赖好的规格、独立检查器、测试、可观测性和清晰接口：让判断也能够跟上生产，让人的注意力花在最值得判断的地方。

## 2. 四层方法总表

| 层 | 手段 | 解决的问题 | 出处 | 成本 |
|---|---|---|---|---|
| ① 规格 | 可检查的完成条件、断言 | 先定义什么算「对」 | L1 / L2 / L11 | 最低 |
| ② 输入 | 等价类、边界值、决策表、状态转换 | 让错误有机会暴露 | L11 | 低 |
| ③ 自动化 | 测试金字塔 + CI + 分支保护 | 让检查不可绕过 | L11 / L8 | 中 |
| ④ 专项 | 差分、模糊、属性、蜕变、行为替身 | 标准答案拿不到时怎么办 | L11 / L13 | 中高 |
| ⑤ 形式化 | 不变式、证明助手、PCC | 把「可能对」变成「可验证」 | L12 | 最高 |

下面逐层展开，每层给「原文怎么说」「怎么用」「检查清单」。

## 3. 第一层：把「对」写成可判定的（L1 / L2）

### 3.1 第三人判据

第 2 讲给了一个可以立刻用的判据：

> 一个实用的检查办法是：**让另一个人只看要求和最终产物，能否判断任务已经完成？**「做得专业一点」很难判定；「页面首先展示研究方向和近期工作，手机上无需横向滚动，所有项目入口都能打开」，就提供了可以检查的行为。

操作方式：把需求改写成三行——

```
输入：给什么（数据、环境、前置条件）
预期：看到什么（可观察的行为或输出）
限制：不允许什么（性能、兼容性、安全边界）
```

写不出来的部分，就是模型要替你猜的部分。第 1 讲把这件事的代价讲透了：

> 模型怎样填补这些空白？很大程度上靠猜。……但在架构、数据表示和验收标准上猜错，代价就大得多。

### 3.2 完成的语义包含「失败」

> 完成的语义还包括失败。如果关键条件无法验证，合理的结果应当是**报告哪里没完成、缺少什么证据**，而不是交出一段肯定的总结。

操作方式：在任务描述里显式允许三种结局——完成 / 部分完成（说明缺口）/ 无法完成（说明缺什么）。否则模型倾向于交一个「看起来能跑」的结论。

### 3.3 断言：每个用例三个动作

第 11 讲：

> 每个完整用例都应包含三个动作：**准备环境和输入，执行操作，检查结果**。缺少最后一步，就容易出现 Agent 跑了一大堆命令、得到一大串日志，却没有真正核对核心行为的情况。

> 覆盖告诉我们代码有没有被执行，**断言告诉我们被观察到的结果是否符合要求**，输入的选择则决定错误有没有机会暴露。

### ✅ 第一层检查清单

- [ ] 验收条件能让没参与的人独立判断
- [ ] 每条验收条件都对应至少一条断言
- [ ] 任务允许「报告失败」，并说明了缺什么证据
- [ ] 关键假设（数据类型、边界、错误处理）已显式写出

## 4. 第二层：黑盒测试的四种输入设计（L11）

老师对黑盒的定义：

> 挑选测试输入有两种基本视角。**黑盒测试从规格出发，不依赖实现内部结构**；白盒测试从代码出发，检查哪些逻辑实际被执行过。

### 4.1 等价类划分

> 把预计由同一种规则处理的输入分成一组，从每组挑代表。比如一个最多接受 100 个元素的接口，空数组、允许范围内的非空数组、超过上限的数组，就可能对应不同的处理规则。

### 4.2 边界值分析

> 重点检查 0、1、99、100、101 等容易出现差一错误的位置。

### 4.3 决策表

> 选课时「是否有余量」和「是否满足先修要求」有四种组合，逐一写清应该接受还是拒绝，就不容易只测最顺利的一条路。

### 4.4 状态转换

> 未选课程可以变成已选，已选可以退回未选，那么重复选课、重复退课、退课后重新选课，各自应该怎样处理？

### ⚠️ 前提：预期结果必须由人给出

> 测试之前必须知道预期结果。超过上限时应该拒绝、截断，还是返回某种错误？这是规格问题。**若测试作者也不知道答案，运行程序只是观察现象，还没有完成验证。**

### ⚠️ 盲区：输入再刁钻，也不能代替场景理解

第 11 讲用「测试工程师走进酒吧」的笑话说明：把所有点酒方式都测了，顾客问厕所在哪却出问题。

> 笑话不是说边界值没有用，而是说测试者可能把全部精力放在「怎样点酒」上，却漏掉了用户实际会走的另一条流程。**输入再刁钻，也不能代替对使用场景的理解。**

### ✅ 第二层检查清单

- [ ] 每个参数都做了等价类划分
- [ ] 边界值覆盖 0 / 1 / 上限−1 / 上限 / 上限+1
- [ ] 多条件组合用决策表穷举
- [ ] 有状态迁移的功能画了状态图
- [ ] 至少有一条「用户真实会走的完整路径」用例

## 5. 第三层：让检查有约束力（L8 / L11）

### 5.1 「好」要变成具体条件

> 把「好」变成具体条件：**能构建、测试通过、没有破坏已有功能、满足项目的重要约束**。如果这些条件成立，再把结果发布出去。

### 5.2 有检查 ≠ 检查有约束力

> 不过，有检查和检查有约束力，是两回事。**如果测试失败后仍然能照常合并，检查只是在旁边亮了一盏红灯。**

以 GitHub 为例，原文建议：

- 把特定状态检查设为**合并必须满足的条件**；
- 用**分支保护**约束直接推送与绕过权限；
- **合并队列**检查待合并改动与主干、队列中其他改动的组合。

### 5.3 测试金字塔的分工

> 测试金字塔是一种常见的组织方式：大量快速的单元测试，适量集成测试，少量端到端测试。越靠近局部，通常越容易控制条件、定位失败；越靠近完整系统，涉及的真实因素越多，代价也越高。**它强调的是分工，不是要求所有项目遵守一个固定比例。**

四层测试各自回答不同问题（L11）：

| 层次 | 回答的问题 | 例子 |
|---|---|---|
| 单元 | 一个函数/模块对不对 | 先修判断函数的返回值 |
| 集成 | 模块接起来协作对不对 | 先修服务理解选课服务传的字段 |
| 系统 | 完整流程在目标环境跑通没有 | 登录→选课→刷新仍在 |
| 验收 | 满足用户真实的验收标准没有 | 满员时是否仍允许超额选课 |

### 5.4 CI 阻止，Agent 修正

> 自动检查也应说明**为什么失败、怎样修复**。只返回一个红叉，会让 Agent 花时间猜规则；指出违规依赖的位置与允许的访问方式，才能让下一轮有明确方向。于是形成一个有用的闭环：**CI 阻止，Agent 修正，再由同一套标准验证。**

### 5.5 一条不能越的边界

> 负责实现功能的 Agent，**不能因为过不了检查，就单方面把标准调低**。测试确实可能过时，架构规则也可能需要改变，但修改这些规则需要回到需求和设计理由。**删掉失败断言得到的绿色，与修复程序得到的绿色，颜色相同，含义完全不同。**

这条最适合直接写进团队规范：**任何降低门禁标准的改动，必须由人批准并说明理由。**

### ✅ 第三层检查清单

- [ ] 四种门禁齐备：构建、测试、回归、项目约束
- [ ] 状态检查设成了合并的必要条件（不是提示）
- [ ] 主干禁止直接推送
- [ ] 失败信息包含「哪里错 + 怎么改」
- [ ] 降低标准的改动有审批记录

## 6. 第四层：标准答案拿不到时（L11 / L13）

### 6.1 差分测试：让两个实现互相找茬

> 差分测试（Differential Testing）的想法很直接：**让两份实现从对应的初始状态出发，处理相同输入，再比较结果**。对处理器，可以在指令执行后比较寄存器等体系结构状态，**在首次出现分歧的位置停下来**。

原来是「为什么游戏跑飞了」，变成「为什么执行这一条指令之后两边状态不同」。

课程里的实证：

> 香山的 DiffTest 框架让待测设计与 NEMU、Spike 等参考模型协同执行……运行了 **4 亿个时钟周期**之后，发现香山的 `mstatus` CSR 状态不一致。

**边界**：两边可能误解同一份手册。「结果一致是有用证据，却不是绝对正确的证明。出现分歧以后，还要分析哪一方违反了规格。」

### 6.2 模糊测试：给输入搜索一点方向

> 模糊测试（Fuzz Testing）可以形象地理解为把软件按在地上「摩擦」：不断生成、变异输入，试着把隐藏的错误逼出来。

> AFL 提供了一种**带覆盖反馈的搜索思路**：从已有输入出发进行变异，执行程序，观察是否到达了新的执行路径或状态转移；把有价值的输入留下，继续变异。

**边界**：

> 搜索反馈和正确性检查仍然是两件事。**执行到新代码，说明这个输入值得继续探索，并不说明它已经找到 bug。**

**最有价值的产物**：

> 发现失败之后，留下能重现问题的输入，才能把偶然撞见的异常变成可以调试、可以回归的工程资产。

### 6.3 属性测试：从具体答案转向一般性质

第 13 讲：

> Property-based testing 把关注点从一组指定答案移到一条一般性质。例如，**对合法数据编码再解码，应当恢复原来的内容**。生成器决定测试能看到哪些输入，性质决定它能识别哪些错误；失败后，工具还可以尝试缩小输入，留下更容易理解的反例。

### 6.4 蜕变测试

> 蜕变测试检查**输入经过某种变换后，输出是否仍满足预期关系**。前者需要可信的对照关系，后者需要我们提供正确的变换性质。

### 6.5 行为替身：把难复现的场景做成可反复运行的考场

StrongDM 的做法（L8）：

> 他们还为外部服务建立行为替身，模拟 API 与边界情况，使大量场景能够反复运行。……把它迁移到选课系统，可以设计「**最后一个名额刚被别人占走**」「**请求已成功提交，但响应丢失**」这样的练习环境。

**边界**：

> 替身与真实系统之间的差异也必须验证，否则我们只是造出了一个特别容易过关的考场。

### 6.6 场景化验收：把用户故事放到代码库之外

> Agent 可能用过于简单的实现应付狭窄测试，也可能**修改测试去迁就实现**。为此，他们把端到端用户故事组织为场景，**常放在代码库之外**，作为相对独立的验收依据。

这一条很关键：验收用例如果和实现放在同一个仓库、由同一个 Agent 维护，就等于让考生自己出题。

### ✅ 第四层检查清单

- [ ] 有参考实现时，接了差分比对（含首个分歧点定位）
- [ ] 解析/协议类模块有模糊测试与语料留存
- [ ] 往返、对称、单调等性质写成了属性测试
- [ ] 外部依赖有行为替身，且替身与真实系统的差异被验证过
- [ ] 验收场景独立于实现代码库

## 7. 第五层：形式化（L12）

### 7.1 不变式：一条命题抵过无数次运行

> 循环可能执行任意多次，我们如何用有限篇幅证明它？常见办法是寻找**不变式**：一个在循环开始前成立、每次执行循环体后仍然成立的命题。

课程用的是 Boyer–Moore 多数投票：

> `cnt` 显然不是候选人的真实得票数。真正的不变式是：**已经读过的所有票，都可以分成若干对选项不同的票，以及 cnt 张全部投给 candidate 的剩余票。**

> 这里的前提「存在严格多数」很重要。……**证明不仅告诉我们代码为什么正确，还准确指出了它在什么条件下正确。**

### 7.2 证明助手：铁面无私的反馈

> 课堂上的数学证明，经常省略「显然」的中间步骤。……证明助手把工作台变得十分严格：一边列出「已知什么」，另一边列出「还要证明什么」，我们只能通过允许的规则改变证明状态。**不是敲一句「显然成立」，计算机就会通融。**

对 AI 协作的意义：

> 这种反馈对 Agent 极其有用。它不再只能反复问另一个模型「你觉得我的证明对吗」，而是可以**运行检查，看到哪个目标没有完成、哪个类型不匹配，再修改**。创造证明很难，检查一个已经写清楚的证明却可能机械得多。

### 7.3 携带证明的代码（PCC）

> 如果证明可以更便宜地构造，软件交付的形态也可能变化：**交付代码时，同时交付它满足某项策略的证明，接收方检查证明，再决定是否接受代码。**

> 它把一种责任分工做得很清楚：代码提供者承担构造证明的工作，接收者根据自己的安全策略检查证明。

### ⚠️ 形式化也有边界

> There is no Silver Bullet。形式化的价值，依赖于我们能否用比实现更简洁、独立的方式表达「正确」。

> 「我要一个领导满意的教务系统」，该怎样形式化？……**证明能力增强以后，问题会继续向前移动：从实现是否符合规格，移向规格是否符合意图。**

### ✅ 第五层检查清单

- [ ] 关键循环/算法找到了可陈述的不变式
- [ ] 形式化只用于「能用比实现更简洁的方式表达正确」的部分
- [ ] 证明通过后，仍然单独检查规格是否符合真实意图

## 8. 静态工具怎么选（L13）

第 13 讲的这一节相当于一张「工具适用性对照表」：

| 工具 | 保留了什么 | 忘掉了什么 |
|---|---|---|
| 类型系统 | 值的类型与结构，编译期排除一类错误 | 具体数值、调用时序、业务要求 |
| Linter | 语法模式与团队约定 | 「符合规则」不等于「业务正确」 |
| 抽象解释 | 用区间/符号等抽象值覆盖巨大状态空间 | 近似会带来误报 |
| 单元测试 | 选定输入与预期输出的回归 | 未覆盖的输入、未编码的意图 |
| 模糊测试 | 自动生成/变异输入 + 运行时检测 | 未执行到的行为不获保证 |
| 属性测试 | 一条一般性质 + 反例缩小 | 大量采样≠穷尽输入域 |
| 差分测试 | 多实现互相找茬 | 可能共享同一个错误 |
| 蜕变测试 | 输入变换后的关系 | 需要人提供正确的变换性质 |
| 模型检验 | 模型内全部相关行为 + 反例轨迹 | 保证只属于那个模型 |
| 符号执行 | 沿路径积累约束找触发输入 | 未探索路径与环境简化 |
| 定理证明 | 明确规格下的逻辑保证 | 规格与真实需求的距离仍在 |

原话总结：

> 因此，看到绿色对勾，我们应该问：**它究竟买到了什么？** 看到红色告警，我们应该问：**它究竟留下了什么？** 一个可复现输入、一条反例轨迹和一个未完成的证明目标，代表不同的证据，也决定了不同的下一步。

## 9. 一条可以照着走的流水线

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 把需求写成「输入 / 预期 / 限制」三行，允许报告失败 | 验收条件 |
| 2 | 用等价类、边界值、决策表、状态转换设计用例，**断言由人写** | 测试用例表 |
| 3 | 让 Agent 在规格下生成，不要求它「做得专业一点」 | 实现 |
| 4 | 接 CI：构建、测试、回归、项目约束四项门禁，设为合并必须 | 门禁 |
| 5 | 失败反馈要含「哪里错 + 怎么改」，形成 CI 阻止 → Agent 修正闭环 | 修复 |
| 6 | 核心模块补差分 / 属性 / 模糊测试，留存触发输入 | 回归资产 |
| 7 | 高安全要求走不变式或证明 | 证明 |
| 8 | 交付前问：这个绿色对勾买到了什么？ | 验收结论 |

## 10. 三个最容易踩的坑

### 坑一：覆盖率高就等于对

> 覆盖率高不等于正确。假如加法函数误写成了减法：`def add(a, b): return a - b`。调用 `add(1, 2)` 就覆盖了函数中的计算语句。只有继续检查 `assert add(1, 2) == 3`，才抓住了错误。

### 坑二：测试通过就等于需求满足

第 1 讲：

> 即使程序通过了现有测试，也只能说明它满足了这些检查，**不能自动推出规格忠实表达了真实意图**。

### 坑三：Agent 改了标准，让检查变绿

> 删掉失败断言得到的绿色，与修复程序得到的绿色，颜色相同，含义完全不同。

## 12. 附：可直接用的 prompt 模板

### 模板 A：写验收条件

```
我要做一个 <功能>。
请先不写代码，把它改写成可检查的验收条件，每条包含三部分：
1) 输入/前置条件
2) 可观察的预期结果
3) 不允许出现的行为
要求：一个没参与过这个项目的人，只看这些条件能否判断是否完成。
写完后列出你认为还需要我确认的 3 个关键假设。
```

### 模板 B：让 Agent 自证

```
实现完成后，请给出证据而不是结论：
- 每条验收条件对应哪一条断言/测试
- 实际运行输出的关键片段
- 哪些条件你没有验证，为什么
如果有关键条件无法验证，请直接说明缺什么，不要给肯定结论。
```

### 模板 C：设计黑盒用例

```
对 <函数/接口> 做黑盒测试设计，不参考实现细节：
1) 等价类划分（列出分组依据）
2) 边界值（含上限±1）
3) 多条件组合的决策表
4) 若涉及状态，画状态迁移并列出非法迁移
每条用例给出预期结果，预期结果不确定的单独标注出来。
```

### 模板 D：引入差分测试

```
我有一个待测实现 A 和一个参考实现 B。
请写一个比对脚本：相同输入分别喂给 A 和 B，
逐条比较 <可观察状态>，在第一次出现分歧时停止，
输出输入、双方结果和分歧位置。
不要试图判断谁对谁错，只负责定位分歧。
```
