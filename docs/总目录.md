    - 原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释
  - 2.9　人应该盯住哪些地方

## 第 02 讲　提示词与上下文工程

`2026-09-01` · `98 分钟` · `62309 播放` · [`BV1CQt365EzW`](https://www.bilibili.com/video/BV1CQt365EzW)

**一句话**：模型的行为由它看见的整份上下文决定；你说的最后一句话只是其中一小份。上下文工程就是安排「谁站前排」。

**本讲要回答**：同一句需求，为什么 AI 每次理解得都不一样？

**核心要点**

1. **规则也在争夺注意力** — 把要求写进上下文能让模型反复利用，但「在上下文里」不保证「每次都被遵守」。同一句话放进系统指令和塞进第十层子目录，分量完全不同。
2. **写清楚「完成」是什么** — 判据是：第三人只看要求和产物，能否判断完成没有。「帮我看看性能」不是要求；「给出压测数据、定位瓶颈、说服一个没读过代码的人」才是。完成的语义里还要包含「报告失败」。
3. **大仓库有时比空项目好改** — 空项目处处是路，Agent 每一步都在掷骰子；成熟仓库的命名、分层、测试约定约束了采样空间。代价是模型会模仿历史包袱——技术债在 Agent 时代升值了。
4. **Token 是预算，也是注意力** — 「真正稀缺的不是 token，而是值得花 token 的问题、清晰约束和可靠验收。」按决策影响和返工代价分配注意力：可逆可检验的放手，接口级、不可恢复的动作提前盯。
5. **探索型任务要允许说「没找到」** — 预算耗尽只说明这次没找到，不等于不存在。允许失败被说出来，失败才会早到，返工才便宜。

**本讲结构**

- `2.1` **模型看到的，远不止你刚输入的一句话**
  - 我们习惯把给模型的输入叫作 prompt，中文称“提示词”
  - 但对 Agent 来说，指令分散在很多地方
  - 第一讲里的 Pr[token | context]，其中的 context…
  - 所以，“提示词工程”逐渐扩展成了“上下文工程”：关心模型在做决定时能看到什么，哪些是…
- `2.2` **AI 降低了开始学习的成本**
  - 上下文工程听起来像开发者才需要关心的技术，但学生每天都能用到
  - 现在可以立即把具体问题交给 Agent：给出一个最小例子，逐步推导，运行一段程序，再…
  - 但学习仍然需要自己的活动
  - 这可以理解为让 AI 做一个随时在场的听众
- `2.3` **写清楚“完成”是什么**
  - 模型具有很强的指令遵循能力，但首先要有值得遵循的指令
  - “一句话生成极品飞车”可以产生很漂亮的演示
  - 这就是第一讲的 Intent、Spec 和 Impl 之间的缺口
  - 个人主页是另一个例子
- `2.4` **一步有限，为什么还能完成复杂任务**
  - 一个疑问随之而来：如果模型只是反复计算下一个 token…
  - 一次模型前向计算的结构和深度是有限的
  - 这样，更多 token 就可能换来更多计算深度
  - 为了把指令遵循的难度具体摆出来，课堂给了几道故意刁难人的写作题
- `2.5` **上下文中的规则，也会争夺注意力**
  - 把要求写进上下文，可以让模型在生成过程中反复利用它
  - 提示词还会带来副作用
  - 于是，一个看似合理的修补办法出现了：再加一条永久规则，禁止把用户要求写进注释
  - 更合适的做法，是区分长期适用的简短规则与当前任务需要的细节
- `2.6` **“你是一位审稿人”，还不够**
  - 课堂接着把任务换成论文审稿：假装自己是 ICSE 的审稿人，阅读指定论文，写一份约一…
  - 模型很容易写出一份看起来像审稿意见的文本：总结贡献，列出优点和不足，再给出一个建议
  - 论文的信息密度非常高
  - 可以把审稿工作拆成三条不同的路线
- `2.7` **为什么大仓库有时比空项目更容易**
  - 课堂提出了一个有趣的观察：从零做一个看起来不难的产品，AI…
  - 可以从上下文的角度理解这种差别
  - 空项目恰好相反
  - 这里不能推出“大仓库一定好改”，或者“模型会自动认出最佳实践”
- `2.8` **Token 花完了，研究为什么还没有推进**
  - 能够执行长程编程任务，意味着模型在遇到错误后仍能继续：修改、构建、测试、观察，再修复
  - 但把任务交给更强的模型、投入更多 token，并不保证任何长程问题都会收敛
  - 原稿没有给出已经查明的失败原因，因此这里能做的是提出待检验的解释
  - 另一个可能的问题，是任务把“把这个想法实现好”当成了目标，但研究真正需要回答的，可能…
- `2.9` **人应该盯住哪些地方**
  - 既然人了解领域，随时干预是否最好
  - 原因在于，单个任务的完成时间与一天能完成的任务总量，是两个不同目标
  - 这种取舍需要有边界
  - 长任务还会不断产生日志、补丁和工具输出
- `2.10` **在不确定性中探索**
  - 到这里，我们一直在讨论怎样把任务说清楚
  - “帮我考虑几种方案”通常有效，却可能过早结束
  - 课堂用取名字作例子：给一个蒋姓的小孩取好听、又有寄托的名字
  - 要扩大探索，可以先划分空间：从典故、音韵、方言、时代感等不同角度生成候选，再检查出处…

**核心要点**

1. **目录不等于项目** — 优盘坏了代码就没了；打包发邮件也算不上管理。版本管理要保存的不只是现在，还有经过哪些状态、状态之间什么关系。
2. **快照不等于完整复制** — Git 保存的是文件内容、目录树与快照之间的历史关系；一次 commit 还记录父提交、作者、说明，父提交把历史组织成有向无环图。
3. **工作区 / 暂存区 / 历史** — add 到底保存了什么，是这个模型最容易被含糊过去的地方。分清楚三者，才能预测 cherry-pick、rebase 会搬走什么。
4. **哪怕只有 hello.c 也要工程判断** — 判断文件用途而不是背文件名黑名单；提交说明保存「为什么」；一个大小写规则背后可能是踩过坑的设计。
5. **原子变更** — 围绕一个明确意图组织的完整修改，应当能被单独理解、单独验证、单独回退。项目就是由这样的变更推进的。
6. **Agent 并行 → 一人一个工位** — 人是单线程生物，Agent 天生多线程。Git worktree 给每个 Agent 独立工作目录，互不踩脚；三个 Agent 就是三间房，每间都归你装修。

## 第 04 讲　版本管理 (2)

**一句话**：版本管理真正管的不是文件，而是「变化的身份」；当开发者可以并行复制，困难就从写代码转移到协作与合流。

**本讲要回答**：为什么 cherry-pick 想搬走的是「改动」，rebase 却让人觉得「我做的还是那段代码」？

**核心要点**

1. **一堆文件不足以表示项目** — 还要表示分叉、合并、谁基于谁改的。父提交构成 DAG，这正是「快照 + 关系」比「文件集合」多出来的东西。
2. **给变化一个稳定身份** — 以提交为中心的工具里，同一次改动在 rebase 后换了哈希。Jujutsu 一类新工具改为「以变更为中心」，每个变更带稳定 change ID，冲突本身也是可保存的状态，还留完整 operation log。
3. **先分后合，还是先上锁** — 对应 MVCC 与互斥。锁粒度粗了排队到死锁，细了合并成本爆炸。判据是冲突频率与返工代价——这套权衡跟参与者是不是人类无关。
4. **困难转移到协作** — 工具解决的是「怎么不打架」，解决不了「打完架之后要哪一种行为」。机器看得见文本冲突，看不懂取舍，最后仍要有人拍板。
5. **从 MVP 起步** — 做出足够小、又能真正投入使用的版本，检验最关键的假设。你就是包工头：决定先做哪块、怎么接起来、交付的能不能用。

## 第 05 讲　软件工程的来龙去脉

`2026-09-20` · `100 分钟` · `24878 播放` · [`BV1Nyeq6qEt8`](https://www.bilibili.com/video/BV1Nyeq6qEt8)

**一句话**：软件工程史上那些「笨重」的发明——流程、契约、UML——都是对具体失败的回应；LLM 没有取消这些失败，只是把差距移到了判断。

**本讲要回答**：如果自然语言能直接生成程序，中间那些需求文档、契约、模型图还有意义吗？

**核心要点**

1. **能力边界一直在移动** — 每一次「昂贵的能力变成日用品」，都会让上一代的核心技能贬值。这不是第一次，也不会是最后一次。
2. **软件危机的真实来源** — 1960 年代：工具不成熟、程序员贵、硬件更贵；更关键的是——擅长编程并不等于理解客户的业务。这个缺口今天仍然存在。
3. **Royce 其实反对瀑布** — 《Managing the Development of Large Software Systems》常被当成瀑布模型的原典，但他真正在担心的是「一次做完再回头」的返工代价。
4. **把流程看成数据依赖图** — 阶段图的价值不在顺序，而在「哪一步的产出是哪一步的输入」。理解成依赖图，才知道哪些步骤可以并行、哪些必须回退。
5. **契约：调用者与实现者各自承诺什么** — Bertrand Meyer 的设计契约把「这次能跑」和「每次都应成立」分开——这正是 AI 生成代码最容易被混淆的两件事。
6. **图与模型：意义保存在哪里** — 模型包含元素、关系、约束；图只是其中一部分的展示。一张图没画出来的信息，不代表模型里没有。
7. **差距移到了判断** — LLM 让「自然语言 → 程序」这条路可行，以前需要人工补齐的中间步骤经常可以一跃而过。被压缩的是表达成本，不是判断成本。

## 第 11 讲　软件质量保障 (1)

`2026-11-03` · `97 分钟` · `10417 播放` · [`BV1ej4g6xESc`](https://www.bilibili.com/video/BV1ej4g6xESc)

**一句话**：质量保障的起点不是「多测几次」，而是承认：任何程序员（人和 AI）都会一本正经地写出错代码。

**本讲要回答**：「在我机器上能跑」到底说明了什么？

**核心要点**

1. **任何程序员都有「幻觉」** — 人会敲错命令、看错变量、漏改一个字母。AI 的错误只是频率和形态不同，不是性质不同。
2. **运行一个程序需要的条件远比参数多** — 依赖版本、环境变量、文件状态、并发时序、外部服务——「能跑」是一个极其局部的结论。
3. **测试按观察范围分层** — 单元 / 集成 / 端到端 / 用户验收，各自回答不同问题。测试金字塔：越靠近局部越容易控制条件和定位失败，越靠近完整系统涉及的真实因素越多。
4. **黑盒与白盒** — 黑盒从规格出发，不依赖内部结构；白盒从代码出发，检查哪些逻辑实际被执行过。两者回答的不是同一个问题。
5. **差分测试：让两个实现互相找茬** — 当所有测试理论都失效时，你需要的是一个适合当前系统的实验方案。
6. **模糊测试：给输入搜索一点方向** — 不断生成、变异输入，试着把隐藏的崩溃逼出来。有检查机制之后，还要让程序经历足够多、足够有价值的情况。
7. **有些输入不在屏幕里** — 插拔 SD 卡的小机器人：真实系统的输入可能来自物理世界，测试的边界要跟着系统走。

**本讲结构**

- `11.1` **从“能运行”到“能驾驭”**
  - 软件不是一次写完的静态作品，而是在一次次修改中演化的系统
  - 生成式 AI 大幅降低了修改软件的成本，却没有让这两道鸿沟自动消失
  - 现在，我们仍然需要能驾驭软件
- `11.2` **任何程序员都有“幻觉”**
  - 人类程序员也会一本正经地写出错误代码
  - for (int i = 0; i < n; i++) for (int j =…
  - 模型同样不能仅凭“感觉”得到正确程序，尤其是一次写出几百行、还要照顾许多关联约束时
  - 为了讨论错误怎样出现，需要区分三个概念
- `11.3` **“在我机器上能跑”到底说明了什么**
  - 测试看起来是最便宜的质量保障方法：顺便运行几次呗
  - 首先，你的环境不是别人的环境
  - 这也是依赖锁文件存在的原因
  - 其次，即使环境相同，你的运行也不是别人的运行
- `11.4` **从局部测试到用户验收**
  - 软件工程中的测试，首先可以按观察范围分层
  - 单元测试检查一个函数或模块
  - 集成测试检查模块连接起来以后是否协作正确
  - 系统测试面对完整系统，在目标环境中走完流程
- `11.5` **测什么，以及怎样知道测对了**
  - 挑选测试输入有两种基本视角
  - 黑盒测试可以先做等价类划分：把预计由同一种规则处理的输入分成一组，从每组挑代表
  - 测试之前必须知道预期结果
  - 规则涉及多个条件时，可以使用决策表
- `11.6` **让测试成为日常工程**
  - 测试金字塔是一种常见的组织方式：大量快速的单元测试，适量集成测试，少量端到端测试

## 第 12 讲　软件质量保障 (2)

`2026-11-10` · `95 分钟` · `6999 播放` · [`BV1LaW36WErp`](https://www.bilibili.com/video/BV1LaW36WErp)

**一句话**：测试能揭示 bug 存在，通常不能证明 bug 不存在。这一讲把「程序」当成数学对象，看证明能不能变得便宜。

**本讲要回答**：跑过一万个输入都没问题，能不能说明第一万零一个也没问题？

**核心要点**

1. **fault → error → failure** — 程序里有缺陷，不代表这次运行一定进入错误状态；进入错误状态，也不一定表现为可见失败。三者要分开说。
2. **不变式：一个抵过无数次运行** — 循环可能执行任意多次，但找到一个「循环前成立、每次循环体执行后仍成立」的命题，就能用有限篇幅覆盖无限次执行。
3. **Everything is a state machine** — 状态包含变量、内存、各线程执行到哪里；执行一步就是一次状态转移。操作语义给出了这台状态机的规则。
4. **证明助手：铁面无私的反馈** — 它不接受「大概对」，只接受「检查通过」。这种反馈的确定性，正是 AI 生成最缺的东西。
5. **命题即类型，证明即程序** — Curry–Howard 对应把逻辑与编程接起来：证明 P⇒Q 就像构造一个函数。
6. **当 proof 也变成一种 tax** — 如果构造证明的成本降到可以接受，交付形态会变：交付代码时同时交付它满足某项策略的证明，接收方检查证明再决定是否接受——proof-carrying software。
7. **仍然没有银弹** — 证明也只能针对写下来的规格，规格本身是否符合真实意图，仍然是人的问题。

## 第 13 讲　软件分析工具

`2026-11-17` · `91 分钟` · `6061 播放` · [`BV1wysu6hEkz`](https://www.bilibili.com/video/BV1wysu6hEkz)

**一句话**：用软件改进制造软件的方法：每一种工具都是「保留一部分信息、忘掉其余信息」的取舍，理解取舍才知道它什么时候会骗你。

**本讲要回答**：类型检查、静态分析、测试、证明、模型采样——这些工具各自保留了什么，又忘掉了什么？

**核心要点**

1. **程序是数学对象** — 给定执行语义和环境条件，程序的运行可以像单步调试器一样描述：当前状态是什么、执行一步变成什么。这是所有分析工具的公共地基。
2. **每种工具都在做取舍** — 类型系统保留值的类型和结构，把不合法操作排除在执行之前；但它不表达具体数值、调用时序和业务要求。
3. **把程序当作概率分布的采样** — 传统工具假设「人先写规则，工具照着做」。更大胆的做法是让模型在程序空间里采样，再用机制去筛。
4. **策略交给模型，机制仍然关键** — 模型负责「往哪里找」，机制负责「什么算对」。机制不可靠时，策略越强，错得越快。
5. **三个彼此相关的目标** — 语法正确、语义正确、阅读自然——能编译、能跑对、读着像人写的，是三件不同的事。

**本讲结构**

- `13.1` **用软件改进制造软件的方法**
  - 软件是物理世界过程在信息世界的投影
  - 为此，我们积累了许多经验：人月神话提醒我们，增加人手不等于缩短工期；架构设计帮助我们…
  - 回望这段历史，可以把它看成一种“人类 RSI”
  - 到了 AI 时代，这个循环里的一部分也可以交给 Agent
- `13.2` **把程序作为数学对象**
  - 在向 AI 许愿的同时，不要忘记 Computer Science 的根基
  - 测试、分析和验证，从不同方向利用这个根基
  - 但不能因此期待一个“验证一切程序”的算法
  - for a, b, c, n in all_positive_integer_tup…
- `13.3` **每一种工具保留了什么，又忘掉了什么**
  - 类型系统保留值的类型和结构，把许多不合法操作排除在执行之前
  - Linter 根据语法模式和配置规则寻找可疑代码
  - 执行类工具选择另一种取舍
  - Property-based testing（基于性质的测试）把关注点从一组指定答案…
- `13.4` **把程序作为概率分布的采样**
  - 传统工具的基本假设是：人先写规则，工具再照着做
  - 这并不是说，确定性程序的下一条指令忽然随机了
  - def f(x): return not x.foo(c1) and x.bar…
  - def can_watch_huang_guo_tv(visitor):…
- `13.5` **策略交给模型，机制仍然关键**
  - 老师用一句改写的口号表达这种变化：
  - Heuristics is dead, Policy is Heuristics,…
  - Heuristics 是启发式方法，Policy 是决定做什么的策略，Mechani…
  - 这句口号当然不意味着启发式算法真的全部消失
- `13.6` **软件工程工具的未来**
  - 软件生成面临三个彼此相关、又不相同的目标：语法正确、语义正确、阅读自然
  - 这个开放问题解决了吗
  - 尤其要注意架构失败
  - 因此，反馈不能只覆盖眼前的功能，还要覆盖未来修改的代价
